New findings in updated firmware (3 items — none block flash)

NEW-01 — Low — main.cpp:212
firebaseCooldownUntilMs = millis() + 10000UL in the WiFi reconnect path. This is the same unsafe addition pattern fixed by M-20 in connectivity_cloud.cpp, but was introduced here in the updated main.cpp. At the ~49-day millis() rollover, the sum overflows and sets the cooldown deadline to a value in the past, causing it to immediately expire — meaning the 10-second post-reconnect grace period is skipped. Impact: Firebase may attempt token refresh slightly too early after a WiFi reconnect at the 49-day mark. This is a cosmetic reliability issue, not a safety issue. Fix: replace with firebaseCooldownUntilMs = addMillisSaturated(millis(), 10000UL).
NEW-02 — Cosmetic — main.cpp:320,385
Two routine telemetry log calls use LOG_LEVEL_ERROR instead of LOG_LEVEL_INFO:
• Line 320: LOG(LOG_LEVEL_ERROR, "SENSOR", "Level:%d%%...") — fires every 1s sensor interval even when everything is healthy.
• Line 385: LOG(LOG_LEVEL_ERROR, "TELEM", "Ultrasonic ok/timeout...") — fires every 60s unconditionally.
Impact: Every healthy sensor reading and every 60-second telemetry summary will appear as an ERROR in syslog and Firebase error logs, making real errors harder to spot. No functional impact on pump control. Fix: change both to LOG_LEVEL_INFO.
NEW-03 — Cosmetic — main.cpp: loop sleep block
The sleep wake calculation nextWake = lastSensorMs + SLEEP_WAKE_INTERVAL_MS uses raw unsigned addition without overflow protection. If lastSensorMs is near ULONG_MAX (at 49-day rollover), nextWake overflows. The guard (nextWake > now) ? (nextWake - now) : 1000 then sees nextWake < now and clips to 1000ms minimum sleep — so the device wakes every 100ms instead of 30s. Impact: During sleep mode at exactly the 49-day rollover, the device polls at maximum rate for one sensor interval (~1s) then recovers normally. No safety impact; pump stays off during sleep. Fix: use addMillisSaturated(lastSensorMs, SLEEP_WAKE_INTERVAL_MS).
